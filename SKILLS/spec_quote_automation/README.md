# スキルモジュール: 営業〜技術の仕様選定・見積自動化（spec_quote_automation）

- **発祥部門**: sales × engineering（部門横断）
- **ステータス**: 提案（未実証。`02_SOLUTIONS/sales` `02_SOLUTIONS/engineering` での実証を経て資産化する）
- **由来診断・ソリューション**: 未登録（`01_DIAGNOSTICS/sales` および `01_DIAGNOSTICS/engineering` に対象診断が起票され次第、紐付ける）

## 1. 目的・対象業務

「お客様ごとに違うから標準化できない」という営業部門の言い分を第一原理で分解し（RULES.md 2.1 Deconstruction）、顧客要求から仕様選定・見積作成までのプロセスのうち、定型化可能な部分（技術的制約確認・仕様パラメータの組み合わせロジック・価格ロジック）と、真に属人性が必要な部分（顧客との関係構築・交渉）を分離する。営業と技術・生産技術の間で往復していた仕様確認のやり取りを、構造化された仕様選定ロジックとして自動化し、提示までのリードタイムを短縮する。

## 2. 入力・出力

- 入力: 顧客要求事項、`design_knowledge_structuring` で構造化された技術的制約・設計判断ロジック、過去の類似案件の仕様・見積データ
- 出力: 技術的制約を満たす仕様選定候補、見積書のたたき台（ドラフト）、参照した過去案件・制約条件の一覧

## 3. 前提条件・使用データ

- 必要なデータ・システム連携: 過去の見積・仕様データの蓄積、技術部門の設計制約データ（`design_knowledge_structuring` との連携）
- データの機密区分（RULES.md 6章参照）: 顧客情報・見積・契約条件（機密性: 高、営業側）、図面・設計仕様（機密性: 高、技術側）。外部AIサービスへの投入前に顧客名・個人情報のマスキング必須

## 4. Human-in-the-Loopチェックポイント（必須）

| ステップ | AIが行うこと | 人間が確認・承認すること |
|---|---|---|
| 仕様選定候補の提示 | 技術的制約データと顧客要求を突き合わせ、仕様選定候補を提示する | 技術的妥当性の最終確認は技術・生産技術部門が行う |
| 見積たたき台の作成 | 過去案件を参照して見積書のドラフトを作成する | 価格条件の最終決定は営業担当者・上長が判断する |
| 顧客への提示 | 提示には関与しない（対象外） | 仕様書・見積の最終確定と顧客への提示は、必ず営業担当者が行う（RULES.md 1.3） |

## 6. 限界・注意点

- 特殊仕様・新規性の高い案件では、参照できる過去の技術的制約データが少なく精度が下がる。技術部門への確認を省略しない。
- ドラフトをそのまま顧客に提示することは想定していない（RULES.md 1.3、営業部門の「顧客関係が薄れる懸念」への配慮）。
- `design_knowledge_structuring` が未整備の領域では、技術的制約の自動確認ができず適用範囲が限定される。
