- **発祥部門**: sales
- **ステータス**: 提案（未実証。`02_SOLUTIONS/sales` での実証を経て資産化する）
- **由来診断・ソリューション**: 未登録（`01_DIAGNOSTICS/sales` に対象診断が起票され次第、紐付ける）

## 1. 目的・対象業務

業務プロセスの再設計（BPR）を行う際に、As-Is（現状業務フロー）とTo-Be（改革後の業務フロー）を構造化して記述し、変化する役割・責任・承認プロセスを明示するための共通フォーマット。当初は営業の見積・提案プロセス再設計から生まれたが、部門を問わずBPRを伴うソリューション（`02_SOLUTIONS/<部門>/bpr/`）全般に適用する汎用フレームワーク。

## 2. 入力・出力

- 入力: 現状業務フローの記述（担当者・ステップ・承認者・所要時間）、改革後の業務フローの設計案
- 出力: As-Is/To-Be対比図、変化する役割・責任・承認プロセスの一覧、削減される工数・リードタイムの試算根拠

## 3. 前提条件・使用データ

- 必要なデータ・システム連携: 対象業務プロセスの現状の実測データ（所要時間・承認フロー等）
- データの機密区分（RULES.md 5章参照）: 対象部門・対象データに応じて異なる。営業案件では顧客情報・見積条件が含まれる場合、匿名化を必須とする

## 4. Human-in-the-Loopチェックポイント（必須）

| ステップ | AIが行うこと | 人間が確認・承認すること |
|---|---|---|
| As-Is/To-Be案の作成 | 現状データからAs-Isを構造化し、To-Be案のたたき台を作成する | プロセス変更の妥当性・実現可能性を対象部門の責任者が判断する |
| 承認プロセスの変更提案 | 変化する承認プロセスの候補を提示する | 承認権限の変更は必ず改革オーナー・対象部門責任者が承認する |
| 顧客提示情報が関わる場合 | 判断には関与しない（対象外） | 顧客への最終提示情報の確定は必ず人間が行う（RULES.md 1.3） |

## 6. 限界・注意点

- 現状業務フローの実測データが不十分な場合、As-Isの精度が下がる。
- To-Be案は「あるべき論」に留まりがちなため、必ず小規模実証（RULES.md 4章）を経てから全面移行の判断をする。
