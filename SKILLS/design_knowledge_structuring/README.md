# スキルモジュール: 技術設計ナレッジの構造化（design_knowledge_structuring）

- **発祥部門**: engineering
- **ステータス**: 提案（未実証。`02_SOLUTIONS/engineering` での実証を経て資産化する）
- **由来診断・ソリューション**: 未登録（`01_DIAGNOSTICS/engineering` に対象診断が起票され次第、紐付ける）

## 1. 目的・対象業務

「設計には経験が必要で標準化できない」という技術部門の言い分を第一原理で分解し（RULES.md 2.1 Deconstruction）、過去の設計判断・トレードオフ根拠・却下案とその理由を、検索・再利用可能な形式知として構造化する。図面・仕様書・設計レビュー議事録から、判断ロジック（なぜこの仕様を選び、なぜ別案を却下したか）を抽出し、設計者の暗黙知のうち形式知化可能な部分を可視化する。

## 2. 入力・出力

- 入力: 過去の図面・設計仕様書・設計レビュー議事録、設計変更履歴（なぜ変更したかの記録があれば含む）
- 出力: 設計判断ロジックの構造化データ（条件→採用案／却下案→理由）、類似設計案件の検索結果と出典（一次情報への参照）

## 3. 前提条件・使用データ

- 必要なデータ・システム連携: 設計資産の電子化・検索可能な形での蓄積（レビュー議事録に判断理由が記録されていること）
- データの機密区分（RULES.md 6章参照）: 図面・設計仕様・特許等の知的財産（機密性: 高）。外部AIサービスへの投入は原則不可、社内環境での運用を前提とする

## 4. Human-in-the-Loopチェックポイント（必須）

| ステップ | AIが行うこと | 人間が確認・承認すること |
|---|---|---|
| 判断ロジックの抽出・構造化 | 過去資料から設計判断ロジックの候補を抽出し提示する | 抽出結果の技術的正確性を設計者・設計レビューが確認する |
| 類似設計案件の検索 | 関連候補を出典付きで提示する | 新規設計への適用可否は設計者が判断する |
| 設計判断への反映 | 判断には関与しない（対象外） | 新規設計の採用・不採用の最終判断は設計者・設計レビューが行う（RULES.md 1.3） |
| 社外共有 | 判断には関与しない（対象外） | 構造化された設計ナレッジを社外に共有する場合、知財部門・上長の承認を得る |

## 6. 限界・注意点

- 判断理由が記録されていない過去資料（結果のみが残る図面等）からは、判断ロジックを抽出できない。
- 技術的な正しさ・実現可能性の判断は代行しない。あくまで「候補・構造化データの提示」に留まる。
