# 部門横断メタ真因統合分析（META_ROOT_CAUSE_SYNTHESIS）

- **作成者**: ジョブズ（AI Chief Visionary Officer）
- **作成日**: 2026-08-10
- **目的**: `DIAG-20260810-01〜04`（4部門個別診断）の結果を統合し、部門ごとに別々に見えていた真因が、実は共通の本質的課題に収束していないかを検証する。RULES.md 2章「思考アルゴリズム」の適用範囲を、単一部門の分解（Deconstruction）から部門横断の統合（Meta-Synthesis）へ拡張する根拠として使用する。

## 統合分析の必要性

第一原理診断は部門ごとに独立して実施したが、4件を並べて読むと、表面的には異なる訴え（検査工数・設計調査・突発停止・見積リードタイム）が、構造的にはほぼ同じパターンを共有していることが分かる。これを見落とすと、4部門に対して4つの似て非なるソリューションを個別に設計してしまい、投資が分散し、かつ本来1つの基盤投資で解決できる問題を4回解くことになる（RULES.md 1.2 定量インパクト必須の観点で非効率）。

## 4診断の真因の並置

| 診断ID | 部門 | 真因（個別診断時点の記述） |
|---|---|---|
| DIAG-20260810-01 | 製造 | 検査基準・判定ロジックの未言語化により、専門判断とルーティン判定が分離されていない |
| DIAG-20260810-02 | 技術 | 設計判断根拠の記録・検索インフラが存在せず、「経験」が実際には「検索コスト」を指している |
| DIAG-20260810-03 | 生産技術 | 工程条件の最適範囲が更新されないまま放置され、経験的補正に依存する運用が固定化している（異常予兆の検知インフラの欠如） |
| DIAG-20260810-04 | 営業 | 技術的制約情報の非対称性（技術部門にしか存在しない）が営業側の往復工数として顕在化している |

## メタ真因（共通の本質的課題）

4件はいずれも**「専門判断のロジック・根拠が、個人の頭の中にのみ存在し、組織的に構造化・検索可能な形で蓄積されていない」**という同一パターンの部門別現れである。

- 製造＝判定基準が構造化されていない
- 技術＝設計判断根拠が構造化されていない
- 生産技術＝工程条件の最適値・更新履歴が構造化されていない
- 営業＝（自部門ではなく）技術部門の情報が構造化されていないことの被害を受けている

**メタ真因**: 当社には、専門判断の根拠を捕捉・構造化・検索可能にする共通の「ナレッジ基盤」が存在せず、各部門がこれを個別に（そして場当たり的に）人的な記憶・経験で代替している。

## 部門間の依存関係

4診断のうち、`DIAG-20260810-04`（営業）は自部門の真因ではなく、`DIAG-20260810-02`（技術）の真因が未解決であることに起因すると明記されている。すなわち、**技術部門のナレッジ構造化（`SKILLS/design_knowledge_structuring`）が解決されない限り、営業部門の真因は独立には解消できない**。

```
DIAG-02（技術: 設計判断根拠の非構造化）
   └─ 前提となる ─→ DIAG-04（営業: 見積・仕様確認の往復）
DIAG-01（製造: 検査基準の非構造化）  … 独立して解決可能
DIAG-03（生産技術: 工程条件の非構造化） … 独立して解決可能、ただし解決手法(Weibull解析等)はDIAG-01のSPC手法と構造的に類似
```

## 戦略への示唆（`00_STRATEGY/PROPOSALS/PROP-20260810-01` への影響）

1. **パイロット選定基準の見直し**: 従来の「単一部門の構造的損失の大きさ」だけでなく、「他部門への波及効果（他の真因の解消の前提になっているか）」を優先順位の基準に加えるべきである。技術部門（DIAG-02）は単独のROIだけでなく、営業部門（DIAG-04）の解決を可能にする波及効果を持つため、優先度を実質的に押し上げる要因になる。
2. **`SKILLS/design_knowledge_structuring` の位置づけの見直し**: 他の4スキルと並列の「1モジュール」ではなく、`spec_quote_automation` が明示的に依存する**基盤スキル**である。今後、ナレッジ構造化の設計（データ構造・検索方式）を汎用化できれば、製造（`qc_story_audit`）・生産技術（`weibull_reliability_analysis`）にも転用できる可能性が高い（判定基準・工程条件も「専門判断ロジックの構造化」という同じ問題の変種であるため）。
3. **教育プログラムの設計への反映**: `02_SOLUTIONS/action_learning_program/` のコホートを部門ごとに完全に独立させるのではなく、技術部門のコホートの成果物（構造化スキーマ）を、後続の他部門コホートが再利用できるよう、実施順序を意図的に設計する。
