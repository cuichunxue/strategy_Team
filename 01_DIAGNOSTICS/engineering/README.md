# 技術部門（engineering）

## 業務特性・評価軸

- 図面・設計仕様・特許等の知的財産を扱う。設計レビュー、技術伝承（暗黙知の形式知化）が重要テーマ。
- 専門性・技術的正しさへのこだわりが強く、根拠の薄い提案には厳しい。

## 典型的な"言い訳"（要検証）

- 「設計には経験が必要で標準化できない」
- 「うちの製品は特殊だから他社の事例は当てはまらない」

マッケンジーはこれらを鵜呑みにせず、`DIAGNOSTIC_TEMPLATE.md` に沿ってなぜなぜを重ね、真因を検証する。

## マッケンジーが疑うべき構造的ボトルネック仮説

- 標準化できないとされる「経験」の中に、実は形式知化可能な判断ロジック（過去の設計判断・トレードオフの基準）が埋もれていないか。
- 設計レビューのボトルネックが、技術力ではなく検索性（過去資産にたどり着けない）に起因していないか。

## 対応方針

- 提言は設計レビューのプロセス（要求仕様→設計→レビュー→検証）に接続しつつ、技術的根拠を定量データで裏付ける。
- 知財・機密情報の外部送信リスクを常に最優先で確認する（RULES.md 5章 データガバナンス参照）。
- 設計判断（技術的な最終承認）は、必ず人間が行う（RULES.md 1.3、Human-in-the-Loop）。
