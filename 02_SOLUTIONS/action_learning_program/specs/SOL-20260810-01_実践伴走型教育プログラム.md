# プロトタイプ仕様書: 実践伴走型（Action Learning）教育プログラム

- **部門**: manufacturing / engineering / production_engineering / sales（部門横断、カリキュラムは部門別に個別設計）
- **対象診断ID**: `01_DIAGNOSTICS/LATENT_NEEDS_DIAGNOSIS.md`（4部門共通の潜在ニーズ診断）
- **ソリューション名**: 実践伴走型（Action Learning）教育プログラム
- **担当**: マッケンジー（AI Managing Partner） / 改革オーナー承認
- **期間**: パイロット期間 未定（改革オーナー承認後、`00_STRATEGY/PROPOSALS/` の提案書で選定された部門から開始）

## 1. 特定された真因・解くべき本質的課題（診断結果の要約）

`LATENT_NEEDS_DIAGNOSIS.md` の分析により、4部門に共通する構造が判明している。

- 各部門が語る抵抗（「AIに判断を奪われる」「標準化できない」等）の正体は、AIそのものへの拒絶ではなく、**「自分の専門性が評価されないまま代替されること」への恐怖**である。
- 真の潜在ニーズは、**「非付加価値作業（検査基準の言語化、過去判断の検索、保全タイミングの整理、確認往復）からの解放」**であり、専門判断そのものの放棄ではない。

したがって、AIツールの操作方法を教える一方向の研修（座学・デモ）では、恐怖は解消されず、構造的損失も残る。**本人の実課題を本人と一緒に解く体験**を通じてのみ、「専門性は奪われず、非付加価値作業だけが減る」ことを実感させられる。

## 2. ソリューション概要

### 2.1 設計思想

「AI研修」という名称・体裁を採らない。あくまで**「持ち込んだ実課題を、その場で解決する伴走セッション」**として設計し、AI活用はその過程で自然に習得される副産物と位置づける。

### 2.2 プログラム構造

- **単位**: 部門ごとの小規模コホート（4〜6名）
- **持ち込み条件**: 各参加者は、現在未解決の実課題・実データを1件以上持参する（例: 製造＝未解決のなぜなぜ分析、技術＝時間のかかっている過去設計調査、生産技術＝原因不明の設備アラート、営業＝作成中の見積・提案書）
- **セッション構成**（1コホートあたり）:

| 回 | 内容 |
|---|---|
| キックオフ | 各参加者の実課題を共有し、`LATENT_NEEDS_DIAGNOSIS.md` の該当部門の真の潜在ニーズと接続して目的を明示する |
| ワークセッション×2〜3回 | マッケンジーの facilitation のもと、実課題をAIとともに実際に解く。並行して、後述のHuman-in-the-Loop共同進行者が専門的正しさを都度確認する |
| ラップアップ | 得られた成果物・再現可能なロジックを振り返り、`SKILLS/` 登録候補として言語化する |

### 2.3 部門別カリキュラム接続（`LATENT_NEEDS_DIAGNOSIS.md` との対応）

| 部門 | 持ち込む実課題の例 | 接続する真の潜在ニーズ |
|---|---|---|
| 製造 | 未解決のなぜなぜ分析・QCストーリー | 勘・コツの継承、見逃しリスクの分散（`SKILLS/qc_story_audit`） |
| 技術 | 時間のかかっている過去設計・仕様の調査 | 相談待ちボトルネックの解消（`SKILLS/design_knowledge_structuring`） |
| 生産技術 | 原因不明の設備アラート・保全計画 | 保全判断の負担・責任の分散（`SKILLS/weibull_reliability_analysis`） |
| 営業 | 作成中の見積・提案書 | 非付加価値作業からの解放（`SKILLS/spec_quote_automation`） |

### 2.4 使用技術

- LLMによる対話的な分析支援・文書化支援（既存 `SKILLS/` モジュールをベースに、セッション中の実課題に合わせて調整する）
- 使用データ範囲: 参加者本人が持ち込む実業務データ。RULES.md 6章（データガバナンス）に従い、顧客情報・図面等の機密データは事前にマスキング要否を判定する。マスキングが困難な場合は、当該回のみ社内閉域環境で実施する。

## 3. Human-in-the-Loopチェックポイント（必須・RULES.md 1.3準拠）

実課題（実データ）を扱うプログラムであるため、通常のソリューション実証以上に厳格な人間の関与を設計する。

| ステップ | AIが行うこと | 人間が確認・承認すること |
|---|---|---|
| 実課題の分析・たたき台作成 | 参加者が持ち込んだデータを分析し、たたき台（要因候補・検索結果・見積案等）を提示する | 各部門の専門性を持つ共同進行者（品質保証／設計レビュー担当／生産技術責任者／営業マネージャー）が、その場で技術的・業務的な妥当性を確認する |
| 品質保証・設備安全・顧客提示に関わる成果物 | 分析・たたき台の提示に留まる | セッション内で完結させず、通常業務の承認フロー（合否判定・出荷可否・設備稼働判断・顧客提示）を経てから正式に反映する（セッションはあくまで「たたき台作成の伴走」であり「意思決定の場」ではない） |
| 実データの外部送信 | 判断には関与しない（対象外） | マスキング要否・送信可否は、セッション開始前にマッケンジーと共同進行者が事前レビューする |

## 4. BPR（業務プロセス再設計）

- As-Is（現状の教育プロセス）: `bpr/ASIS_TOBE.md` を参照
- To-Be（Action Learning後の教育プロセス）: `bpr/ASIS_TOBE.md` を参照
- 変化する役割・責任・承認プロセス: 「講師が教え、社員が聞く」から「社員が課題を持ち込み、マッケンジーが伴走し、共同進行者が専門性を保証する」に変わる。セッションの成果物は個人のノートで終わらせず、`SKILLS/` 登録候補として組織資産化する経路を必須とする。

## 5. 評価指標（定量インパクト・RULES.md 1.2準拠）

研修満足度アンケートのような迎合的指標を主要KPIにしない。行動変容・資産化・実課題の解決という「結果」で測る。

| 指標 | 現状（ベースライン） | 目標 | 前提条件・誤差幅 |
|---|---|---|---|
| 持ち込み課題の解決率 | 0%（セッション未実施） | セッション内でたたき台完成まで到達した課題の割合 70%以上 | 課題の複雑度により変動、パイロットで再設定 |
| セッション後の自走適用率 | 未測定 | セッション終了90日後、参加者が同種の課題に自力でAIを適用できている割合 50%以上 | 参加者への追跡ヒアリングが必要（未整備） |
| SKILLS登録率 | 0件 | セッション成果物のうち `SKILLS/` 登録候補として言語化される割合 30%以上 | 登録基準は `SKILLS/README.md` の手順に従う |
| 参加者1人あたりの解決時間短縮 | 参加者自身の「一人でやった場合の想定時間」を事前申告してベースラインとする | セッションでの実測時間との差分をROI試算根拠として `00_STRATEGY/ROI_LEDGER.md` に記録する | 自己申告ベースのため誤差幅は大きい。複数回実施で補正する |

「研修満足度」は補助指標としては収集するが、投資継続判断の主要指標にはしない。
