# 02_SOLUTIONS

`01_DIAGNOSTICS/<部門>` で真因・定量インパクトが特定された課題について、部門別に改革ソリューションを設計・実証する場所。プロトタイプ仕様書・自動化コード・BPR（業務プロセス再設計）業務フローの3点セットで構成する。第一原理診断を経ていない課題をここで扱わない（RULES.md 1.1）。

## サブディレクトリ

| ディレクトリ | 部門 |
|---|---|
| `manufacturing/` | 製造 |
| `engineering/` | 技術（開発・設計） |
| `production_engineering/` | 生産技術 |
| `sales/` | 営業 |

各部門ディレクトリの構成は共通:

- `specs/` — プロトタイプ仕様書（`SOLUTION_SPEC_TEMPLATE.md` を使用）。対象診断ID、ソリューション概要、評価指標、期間、使用データの範囲、Human-in-the-Loopチェックポイントを明記する。
- `scripts/` — 自動化コード（分析コード、プロンプト等のLLM活用資産を含む）。1ソリューションにつき1サブフォルダを基本とする。
- `bpr/` — BPR業務フロー。As-Is（現状業務フロー）とTo-Be（改革後の業務フロー）を対比した図・文書。

## 運用ルール

1. 実証を始める前に、当該部門の `specs/` にプロトタイプ仕様書を作成し、`01_DIAGNOSTICS/<部門>` の対象診断IDと紐付ける。
2. Human-in-the-Loopチェックポイント（RULES.md 1.3）を仕様書に明記する。品質保証・設備安全・顧客提示情報に関わる最終判断をAI単独に委ねる設計は不可。
3. 使用データは RULES.md 5章（データガバナンス）に従う（原則サンプル化・匿名化データ）。
4. 実証結果（うまくいった／いかなかった）は、成否に関わらず記録し、定量インパクトの実績値を `00_STRATEGY/ROI_LEDGER.md` に反映する。
5. 定量インパクトが確認された実証は、`SKILLS/` にモジュール化して移管し、他部門への横展開可能性を検討する（RULES.md 1.4）。
