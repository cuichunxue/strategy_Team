# セキュリティガイドライン（SHOULD）

`SECURITY_RULES.md` が「絶対に守るべき最低ライン」であるのに対し、本ガイドラインは日々の判断で迷ったときの実務的な目安を示す。ルールとガイドラインが矛盾する場合はルールを優先する。

## 1. データ最小化の考え方

- PoCの最初の一歩は「本当にそのデータ項目が必要か」を問うことから始める。なぜなぜ分析と同様に、目的（何を判定・予測したいか）から逆算して必要最小限のデータ範囲を定める。
- 現場から預かるデータは「検証が終わったら破棄する」ことを前提に扱い、検証終了時に破棄・匿名化状況を記録する。

## 2. 現場との信頼構築

- 現場にデータ提供を依頼する際は、「何のために・どこまでの範囲で・誰が見るか」を必ず先に説明する。無断でのデータ収集・カメラ設置・センサー設置は行わない。
- なぜなぜ分析やQCストーリーの記録をAIで解析する場合、個人の失敗を評価・査定に使わないことを明示し、あくまで「工程改善」目的であることを繰り返し伝える。

## 3. モデル・提案の説明可能性

- 画像認識・異常検知等のモデルは、判定根拠（ヒートマップ、寄与度の高い特徴等）を可能な限り可視化し、現場のなぜなぜ分析と接続できる形で提示する。
- LLMを用いた文書生成・要約（QCストーリー作成支援等）は、生成結果に一次情報（元データ・元記録）への参照を残し、後から検証可能にする。

## 4. 段階的導入の目安

- 目安として、PoC → 1ライン実証 → 効果確認・現場ヒアリング → 水平展開、の各段階を最短でも1サイクルは経てから次段階に進む。
- 効果確認では、定量指標（例: 検出精度、作業時間、不良流出件数）と定性指標（例: 現場の受容度、ヒヤリハットの声）の両方を評価する。

## 5. インシデント時の初動

- データ漏えい・誤送信・意図しない外部送信の疑いが生じた場合は、まず対象データの利用停止・共有停止を行い、直ちに推進リーダーへ報告し `LOGS/` に経緯を記録する。原因究明・恒久対策はその後で行う。
